Build an offline travel journal with NgRx

Most offline support stops at caching screens or retrying one request. Real applications also need to create related records before server IDs exist. NgRx Offline persists those mutations and resolves their local references during replay. Application code still uses the usual NgRx actions, reducers, effects, and selectors. Optimistic updates simply begin with the durable queued action instead of requested.

How the example works

The definitions, provider setup, worker, and reducer used by Atlas Journal.

Complete source

Alpha status

NgRx Offline is ready for evaluation, but it is not yet recommended for production use. Public APIs may change before 1.0.

If it solves a problem in your application, share your use case, missing requirements, or API feedback in the GitHub issue tracker. Continued development toward a stable release will be guided by real-world use and contributor interest.

Define

Name the operation and entity, then describe the HTTP request. Tagged references are discovered from the input.

Bind

Dispatch requested like any NgRx action. Reducers handle queued and succeeded to update domain state.

Persist

The requested action becomes visible as queued only after its input is written to IndexedDB.

Replay

After an online enqueue or reconnect, one scoped executor resolves references, supplies an idempotency key, and reconciles the server result automatically.

Reference a record created offline

The Travel Day input stores a typed reference to its Trip. The request resolves that reference immediately before transport, after the Trip has a server ID.

  • Definitions do not depend on Angular or browser globals.
  • Version 1 and dependency discovery are automatic.
  • Conventional client and server IDs map without extra callbacks.

Configure the Angular provider

The provider registers NgRx effects, IndexedDB persistence, browser coordination, connectivity, and transport. Each operation belongs to an immutable scope.

  • Payloads stay out of the outbox’s NgRx projection.
  • Online writes replay automatically after the durable commit.
  • Logout policy controls preservation or deletion by scope.
  • Browser coordination permits only one active executor.

Optional service-worker replay

The optional worker uses the same definitions, IndexedDB schema, and scoped lock as the foreground adapter. It writes durable receipts; Angular consumes them now or after the next launch.

  • Explicit messages work without Background Sync support.
  • Credentials are enhanced at execution time, never stored in operation input.
  • If the worker lacks credentials, foreground replay handles the queue later.

Update state after IndexedDB succeeds

Application reducers handle the binding’s queued action, not the initial requested action. If IndexedDB rejects the write, the optimistic entity never appears and an enqueue-failed action explains why.

  • Restore actions rebuild optimism after a reload.
  • Succeeded actions reconcile client and server IDs.
  • Blocked actions preserve user work for explicit repair.

Scope and limitations

  • Domain data. Your application owns domain state, reads, and cache policy.
  • Store persistence. Only explicitly registered mutation inputs enter the outbox.
  • Conflict handling. The library surfaces typed failures; your domain decides how to repair them.
  • Server idempotency. Servers must durably store and replay results for each operation key.
